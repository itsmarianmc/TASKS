# Deterministic quick add and calendar rules

`parseQuickAdd(input, graph, aliases = [], context = {}, knownTags = [])` in `src/lib/parser.ts` returns the shared `ParseResult`. It is browser-safe and synchronous. It uses installed chrono-node's German and British English parsers, with strict calendar validation and European numeric overrides. It sends no input to any service, imports no server modules and never reads an API key. Settings labels this first stage `Deterministic · DE + EN`. Optional Gemini fallback is server-only and requires an explicit capture action.

Context is `{projectId?, areaId?, today?, timezone?}`. Production callers pass `timezone` from public config; tests may supply an ISO `today`. Otherwise app-local today uses `Intl.DateTimeFormat.formatToParts` with `Europe/Berlin` as default. An invalid reference date/timezone produces a blocking warning. All date arithmetic uses UTC calendar components, never elapsed milliseconds or the device's calendar timezone.

The pipeline preserves original text spans while comparing case/diacritic/Æ-normalized names. It extracts tags, recurrence and conservative priorities, then protects explicit project/area tokens before parsing dates. It resolves remaining names/aliases, applies context defaults, validates membership and derives title/confidence. Original title spelling is preserved. Whitespace is normalized. No IDs are invented, and stale aliases are ignored. Alias translation (English → Englisch, Homework → Hausaufgaben) requires actual configured aliases; there is no hardcoded production project vocabulary.

## Supported input

- `#Project`, `@Area`, `[tag]`. Known multiword entity names and compact explicit spellings such as `@WebDevelopment` are supported. Tags return names for the existing local tag mutation, with canonical existing spelling when supplied. Explicit new tag names are allowed; new project/area names are not.
- DE/EN today, tomorrow, übermorgen, weekdays, next weekdays, `in 2 weeks`, `in drei Tagen`, named dates such as `7 Oct`, ISO dates, `DD/MM/YYYY` and `DD.MM.YYYY`, and `DD.MM.` without a year. Numeric dates are always European even in English text.
- Explicit `from X to Y`, `von X bis Y`, `vom X bis Y` ranges. A weekday range endpoint is resolved relative to its start. Month/year crossings without an explicit end year carry forward into the next year. Invalid calendar dates, reversed explicit ranges, deadlines earlier than today and several independent date phrases block creation.
- Single dates always mean deadline; start defaults to today. Without a date, start also defaults to today with no deadline. An explicit range supplies both endpoints. This matches the Notion adapter's requirement that a deadline cannot be stored without a start.
- `every 2 weeks`, `alle 2 Wochen`, spelled small numbers, day/week/month/year units, and daily/weekly/monthly/yearly plus German equivalents. Recurrence is removed before date parsing so it cannot be mistaken for a deadline. Intervals are 1–365; competing rules block creation.
- Standalone `!`, `!!`, `!!!` map to medium/high/urgent. Explicit high/medium/low priority phrases and leading or trailing urgent/dringend are supported. Exclamation punctuation within a title is preserved; ordinary mentions of urgent inside a sentence do not set priority.

Explicit relational clauses (`in English`, `as Homework`, `als Hausaufgabe`) are removed from the title. Bare matched subjects are removed when a meaningful title remains; if removing them would produce an empty title, they remain (`Physics homework tomorrow` → `Physics homework`). A long entity name with one edit can resolve only in a marked token or relational clause, with confidence reduced to 0.92 per fuzzy match. Short abbreviations require configured aliases. Ties require a choice. Duplicate aliases remain ambiguous even when the current view suggests one candidate. Existing unique project membership infers its area; multi-area projects require selection. Explicit incompatible relationships always block creation.

`valid` means the title, relations and dates can form a normal task. `needsResolution` is its inverse. `warnings` describe each blocking problem, including missing relations. `confidence` describes the complete parse rather than permission to bypass validation. The UI must retain input, show warnings/pickers, and submit only after a valid parse or validated manual correction. Local Inbox drafts can retain unresolved input; they are not Notion tasks.

## Shared view selectors

`src/lib/views.ts` remains the single source for navigation counts and task lists. Today includes active start/end intervals containing today and overdue incomplete tasks. Next 7 Days uses inclusive overlap with `[today, today + 7]`, including intervals covering the entire window. Missing endpoints are unbounded for overlap; entirely undated tasks are unscheduled. Upcoming uses a start after day seven, or a future deadline when legacy data lacks a start. A deadline-only legacy task can consequently overlap Next and also appear in Upcoming; normal writes always provide a start. Anytime has no deadline. Someday and completed tasks are excluded from ordinary active views. Entity, tag and saved-filter views preserve the ability to display completed/Someday records. A date-bounded saved filter requires a scheduled overlapping interval. Daily highlights derive from Today; Highlight uses the real Notion field.

Results sort incomplete before completed, overdue first, then Highlight, priority, deadline, start, title and ID. Sorting does not mutate source data. `calendarToday`, `isOverdue`, `sortTasks`, `tasksForView`, `dailyHighlights` and existing view metadata exports remain available to UI consumers.

## Boundaries and verification

This is calendar-date parsing, not reminder/time-of-day parsing. Relative weekdays use chrono-node's forward-date conventions. Explicit syntax is available when a title contains a calendar keyword or a shared project/area name. Complex temporal residue such as `before school on Monday` reduces confidence and requires review rather than falsely claiming a fully understood deadline.

## Optional Gemini fallback

Audit before migration: no installed AI SDK, provider client or parsing endpoint existed. Quick Add used the synchronous parser inside `useMemo`, validated fields and relation membership, and saved through the existing guarded creation path. The old provider variables were reserved placeholders only.

Current flow: live deterministic parse → alias/date/context/relation checks → confidence. A valid result at or above `GEMINI_CONFIDENCE_THRESHOLD` (default 0.75) never invokes AI. For uncertain input, **Understand input** or Enter invokes `POST /api/parse`. The server obtains the authoritative graph, aliases and tags, recomputes the deterministic result and gates the optional request again. `src/lib/server/ai/gemini.ts` uses official `@google/genai` 2.27.0 and the stable [Interactions API](https://ai.google.dev/gemini-api/docs/interactions-overview), with `store=false`, text JSON Schema, no tools and no retries. Model: `gemini-3.5-flash-lite`, configurable through `GEMINI_MODEL`.

Only input text, project/area names and IDs, aliases, valid relation pairs, allowed tags, resolved fields, current view and calendar date/timezone reach the provider. Tasks, notes, contact data, attachments, URLs and credentials are excluded. The route accepts no client-supplied graph, reference date or timezone. Server configuration supplies the timezone and current calendar date. The API key is read lazily in a module protected by `server-only`; builds and startup require no key.

Structured output uses the existing ParseResult task fields, including `dates`, `priority: none` and recurrence. The response schema constrains relation IDs and tags. Zod validates JSON and strict types; independent membership, relation, calendar/order, threshold and business-rule checks follow. Resolved deterministic relations/default context and explicit dates, tags, priorities and recurrence cannot be silently replaced. Unknown IDs, incompatible relations and invalid dates reject the entire AI result. Null relations stay unresolved. The default threshold also applies after extraction; model confidence alone cannot bypass validation.

Missing/disabled keys, network/model errors, 429, 5xx, malformed JSON, schema failures, low confidence and timeout keep the deterministic result. The default SDK deadline is 5 seconds, with an AbortController and independent deadline promise. Quick Add gives a short manual-resolution message; logs contain only provider, model, elapsed time, success and a fixed error class. Diagnostics shows `ready` for configured credentials, not a claim of proven connectivity; neither diagnostics nor health invokes the model.

After inference, Quick Add updates the preview and waits for a separate create confirmation. No inference response writes Notion, SQLite, GitHub or Contact. Changes to input/context invalidate old results; input edits abort active requests. In-flight and attempted-input guards prevent repeated Enter from generating duplicate AI calls. Existing creation guards still protect Notion writes. External-item conversion never sends contact/GitHub contents to AI. Offline capture remains local.

Configuration: `GEMINI_API_KEY`, `GEMINI_MODEL=gemini-3.5-flash-lite`, `GEMINI_FALLBACK_ENABLED=true`, `GEMINI_TIMEOUT_MS=5000`, `GEMINI_CONFIDENCE_THRESHOLD=0.75`. Without the optional key, deterministic parsing, manual correction and drafts work normally. Docker keeps its existing env_file and health contract; Gemini configuration has no effect on container health.

New tests mock all provider requests, including an actual installed-SDK roundtrip against a mocked transport. They cover adapter validation, errors/timeouts, configuration, privacy, context preservation, no-AI standard inputs, endpoint boundaries and browser request/preview/confirmation races. No live API calls are part of normal tests.

Tests cover every mandatory specification example, DE/EN dates, European ambiguity, weekday and year-crossing ranges, recurrence/priority prefixes, aliases and fuzzy ambiguity, normalization span preservation, stale IDs, relation conflicts, context, invalid dates, Berlin midnight/DST and all shared view interval/filter/sorting rules. Existing Notion and persistence tests remain active. No live credentials or production fixtures are required for these checks.

Verified on 2026-10-03: TypeScript, ESLint, all 113 Vitest cases (71 parser/calendar/view cases), and optimized Next.js production build passed. Commands used the working `C:\Program Files\nodejs\npm.cmd` runtime because the user's alternative npm shim points to a missing installation; no global runtime configuration was changed.
