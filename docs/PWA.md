# Mobile, PWA and reminders

TÆSKS keeps the same compact hierarchy on desktop and mobile. Desktop has a persistent sidebar; smaller screens use the Lists drawer and a floating capture action. Dialogs retain Radix focus trapping, Escape handling and explicit confirmation. Mobile text inputs use 16px; task/date/source and attachment metadata use at least 10px. Light, dark and system themes update the browser theme color, and the layout accounts for safe-area insets and reduced motion.

## Installation and read caching

`src/app/manifest.ts` declares the TÆSKS name, standalone display and the bundled mint Æ icons: 192px, 512px, 512px maskable and a separate 180px Apple touch icon in `public/icons/`. Settings only exposes an Install action after a real `beforeinstallprompt` event; otherwise it describes the browser menu or Safari's Share → Add to Home Screen.

Service workers and installation require a secure browser context: HTTPS or localhost. An ordinary HTTP LAN address such as `http://192.168.x.x:2015` still serves the app, but does not provide browser offline caching or notification permission. Use HTTPS at the existing reverse proxy for mobile installation. Development mode deliberately does not register a worker.

`GET /sw.js` serves `public/service-worker.js` through `src/app/sw.js/route.ts`, with a version generated for each Next build and no HTTP script caching. Deployment must copy `public/` alongside the standalone server. The worker warms the root HTML and its exact referenced Next assets before publishing its shell. A new worker waits until existing app windows close; activation removes older shell/asset generations. It does not call `skipWaiting` or replace bundles underneath an open app.

Only same-origin GET requests are considered. The shell is the root navigation; static assets, branded icons and the manifest have their own cache. The JSON whitelist is `/api/local`, `/api/graph`, `/api/config`, `/api/github`, `/api/contact` and `/api/notion/schema`. Successful JSON reads use network first and a stored response only after a network exception, with `X-Taesks-Offline` and the original cache timestamp. Force-refresh parameters share their ordinary read key; different pages/searches remain distinct. Read writes are serialized and pruned to 150 entries; assets are pruned toward 512 while retaining the current shell's referenced bundles and icons. An offline banner remains until a fully confirmed online refresh that did not itself fall back to cache.

POST, PATCH and DELETE never enter the worker cache, queue or replay path. `/api/health`, file downloads, uploads and arbitrary routes have no offline fallback. A cached diagnostic remains the last loaded diagnostic, not evidence that an external service is currently connected. New pages and files that were never loaded require a connection. Without an earlier successful visit in this browser, a first offline launch cannot open the app.

Read caches and device drafts contain personal content in this browser profile. Browser storage eviction or clearing site data removes offline copies. Keep the profile private; clearing site storage also removes queued drafts. Server data remains in SQLite after acknowledged synchronization.

## Durable device drafts

Save draft writes a local-storage entry before closing capture. It includes one stable UUID, a separate revision UUID, the original input and the parsed fields/source identity. Inbox labels unacknowledged entries `on this device / queued`. The same ID is used for every retry of the SQLite `saveDraft` upsert; a lost response after a successful write cannot create a second draft. Removal occurs only after a successful response and only if the stored revision still matches that request. Editing during an older acknowledgement keeps the newer version queued.

The open app attempts synchronization when online and every 15 seconds while work remains. Web Locks serialize open windows, with an atomic IndexedDB lease fallback. Offline editing preserves the draft ID; deletion creates a durable tombstone so an earlier write or cached SQLite row cannot reappear. Queued and SQLite copies merge by ID. Device-storage failures keep the input visible and report a recoverable error.

The queue only contains local draft saves/deletions. Invalid IDs, revisions, timestamps or mismatched storage keys are ignored, so a corrupt entry cannot block synchronization of valid drafts. It never creates Notion tasks. A queued draft must be acknowledged by SQLite before explicit Notion conversion is enabled, and existing source/draft conversion ledgers and the ordinary capture uncertain-outcome guard remain in force. Explicit creates still require connectivity and retain durable drafts and uncertainty guards. Other edits can remain optimistic but are visibly unsynced, with explicit Retry after reconnection. The small in-session intent queue never claims server acknowledgement. Pending changes trigger a leave-page warning. Notes and core editor text additionally retain device copies across reopening/reload; file bytes and ordinary task intents are kept for the current open session, not silently replayed by the service worker. See `OPTIMISTIC.md` for limitations.

## Reminders

Reminders are UTC instants in local task metadata. The editor displays device-local wall time; the parser's calendar dates still use `APP_TIMEZONE` (Europe/Berlin by default). Invalid calendar dates, daylight-saving gaps and duplicated wall-clock hours are rejected. An unchanged displayed reminder preserves its original seconds and dismissal state; changing priority/tags/repeat alone does not resurrect a dismissed reminder.

While the app is open, due reminders appear in a compact region and link to the task or its retained local context. Completed tasks are excluded. Dismiss and Snooze 10 min remain visible until SQLite confirms the change; a failed request retains the reminder and its error. Snooze moves the instant by ten minutes and clears dismissal.

Browser notifications use an already granted permission. Permission is requested only from the explicit Settings action. Notification delivery is deduplicated by task ID plus reminder instant with Web Locks, or an atomic IndexedDB claim fallback, and a persistent delivered marker; failed delivery does not acknowledge it. Notification clicks focus an existing app window or open the app and its task/local context. No OS permission prompt is triggered on app launch.

Closed-app Web Push is optional in the production server. Configure the three `VAPID_*` values and an HTTPS `APP_ORIGIN`; then explicitly enable Push on this device in Settings. On iPhone/iPad use a supported iOS version, add TÆSKS to the Home Screen and open that installed app. HTTPS and user consent are required. Browser support is detected through the actual Push/Notification/Service Worker APIs; installation guidance appears before activation when required. The permission prompt never appears at startup. Missing configuration, denied permission and unsupported browsers retain the in-app reminder list.

The server verifies the task directly in Notion before each installation's send and then rechecks local scheduling/dismissal. Unknown completion mappings, unavailable status, archived/deleted tasks and Notion failures authorize no push. The UI graph cache and local completion timestamps cannot authorize delivery. A persistent per-installation task/instant ledger deduplicates accepted sends across restart. Catch-up is limited to 24 hours, transient retries to five attempts, and provider TTL to five minutes. In-flight changes and lost acknowledgements remain races; this is not exactly-once delivery or guaranteed OS delivery.

Push content is generic and includes only a task identifier, reminder instant and stable notification tag; it contains no task titles or notes. The worker always shows a system notification for a valid push and opens the existing task/local-context route when tapped. A device with a confirmed push registration suppresses the open-app system sender, while the in-app reminder remains visible. An offline device retains its last confirmed suppression state. Notification permission alone is not a server subscription. Disable push revokes the server subscription before removing the browser subscription; failures remain visible and can be retried.

The existing worker's update lifecycle is unchanged. If an old worker is still active, Settings asks you to close all TÆSKS windows and reopen before enrollment. Cloudflare Access must protect the whole app including `/api/push`; the origin server must not be publicly accessible around Access. An expired Access session requires sign-in to set up/revoke push or load task content. The push worker itself does not require an Access session to display an already received generic message. The server needs outgoing HTTPS access to the browser push endpoints. See [WEB-PUSH.md](WEB-PUSH.md) for operation, privacy, retry semantics and the pending physical iPhone acceptance test.

## Verification

`tests/pwa.test.ts` covers UUID/ACK and revision races, tombstones, source preservation, storage failure, completed/dismissed reminders, unchanged scheduling, Berlin DST boundaries and notification deduplication/failure. `tests/service-worker.test.ts` executes the actual worker script to verify its whitelist, excluded mutations/health/downloads, parallel cache pruning and marked offline fallback.

`tests/e2e/pwa.spec.ts` uses the actual production service worker, actual local API and SQLite with isolated data. Desktop and iPhone viewport/touch Chromium cases cover shell/read reload offline, lost ACK and retry, offline edit/delete, real reminder failure/dismiss/snooze and two open windows syncing one UUID. Notification permission is a browser fixture, never a real OS prompt. This is installed Edge Chromium coverage; it is not real Safari or a claim of closed-app/background OS delivery. Exact execution results are in `docs/VERIFICATION.md`.
