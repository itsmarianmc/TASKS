# Reliability and security

Notion remains the only core task store. SQLite persists extensions and durable conversion/recurrence outcomes. Integration credentials and authenticated clients are server-only. A secret-value scan of the production browser scripts reported zero matches; logs expose structured operation/status/correlation metadata, not tokens, authentication headers or upstream response bodies. No login system or external schema mutation was introduced.

## Confirmations and races

Notion's graph/schema caches and pending promises carry invalidation generations. Old reads cannot overwrite current state, clear newer work, or supply a pre-write graph after invalidation. Fresh relation verification remains mandatory for task writes. Failed reads retain the original last-success timestamp and explicit stale diagnostics. Scoped pages and updated records must match the requested UUID and configured Tasks source. Data-source query rows also validate their parent. Remote UUIDs normalize, timestamps and date values validate, and unsafe/credential-bearing URLs fail without throwing outside validation. Malformed creates preserve any confirmed UUID in the outcome error. A trash response must confirm matching UUID and true trash state; HTTP success alone is insufficient.

Unknown external/draft conversion outcomes remain durable. The composer now offers **Link an inspected existing task**, with an explicit inspection checkbox and task ID. The route performs scoped GET verification and one synchronous SQLite transaction that checks immutable source, active claims, conflicting IDs and source links before updating both ledgers. It never calls Notion CREATE/PATCH. Direct local source linking also passes through scoped verification. A new server process marks previously interrupted creating claims uncertain only at its first database connection; recurrence claims become failed. Runtime claims are never reset by repository factories or request handling. The supported deployment is one server process/container per data directory; sharing the same SQLite file between independently running application servers is unsupported.

## Ordinary capture

The ordinary editor stores its initial capture revision and uses the existing Web Lock/IndexedDB lease across windows. Inside the lock it rechecks current history and revision before any Notion request or local draft save. Input/pending marker must persist and read back before sending; unavailable/full/corrupt storage or lock failure leaves the input and sends no task. Partial preflight writes roll back. A confirmed marker remains as a revision boundary, blocking an already-open second editor after the first successful ACK. Confirmed captures do not fill a permanent history or impose a 100-task ceiling. Deliberately opening a new editor permits same-text capture again; unconfirmed input remains guarded until inspected/discarded in the branded confirmation. Source/draft ledgers provide additional server protection. PWA still queues only stable-ID local drafts and removes only acknowledged current revisions, never automatic Notion creates.

## HTTP, rendering and files

All mutations use same-Origin checks, JSON validation, bounded streamed request bodies or bounded multipart uploads; cross-site requests and forwarded-host spoofing do not bypass the boundary. Content type must be exactly application/json before parameters. Request routes stay on Node runtime. GitHub remains GET-only through the token's existing permissions and fixed upstream endpoints; Contact calls remain server-side.

Markdown uses react-markdown/GFM without raw HTML. Links accept HTTP/HTTPS without credentials; source remote images are represented as text. Local files use generated private storage UUIDs, safe display names, validated declared signatures/MIME, exclusive creation, physical-write/database rollback, and deliberate confirmed deletion. Downloads force attachment, no-sniff, no-store and sandbox; storage paths never appear in public snapshots. Arbitrary external URLs are not fetched by upload/download APIs.

Production CSP excludes unsafe-eval. Development retains it for the installed Next/React debugging runtime. Next's initial inline bootstrap scripts and inline styles deliberately retain unsafe-inline, following the installed Next non-nonce CSP guide; strict nonce rendering would conflict with the current cached offline shell. Same-origin scripts/connects, denied objects/framing and base/form restrictions remain active. The actual production HTTP header is browser-tested and existing hydrated interactions pass.

Health checks only SQLite quick_check for application success. Notion/GitHub configured states describe setup, not connectivity. Contact reports configured when an explicit endpoint exists and default when its enabled built-in endpoint is used; it is never falsely disabled by an absent variable. Optional service failures do not make the container unhealthy.

## Search scope and limits

GitHub palette search collects every cached dashboard/page and repository section/page, including previously visited contexts. Review/PR identities normalize by repository plus pull number and open actual source data. Cache notifications respond only to successful publication/removal. The palette describes loaded scope, additional/unloaded activity and stale errors. Older unloaded GitHub items require explicit pagination/opening GitHub; a broad remote search was assessed but omitted to preserve scope and avoid eager repository fan-out. Contact's existing debounced, bounded server search remains unchanged. Task-field warnings now use human-readable title/date/assignment guidance without duplicate schema paths.

## Verification and remaining prerequisites

See VERIFICATION.md for exact commands and results. This phase uses a separately managed production server on localhost:3020 and isolated data/reliability-e2e. Its Node child environment explicitly blanks Notion/GitHub tokens and Contact authentication and points Contact at localhost port 9. Existing .env and development data remain untouched in that phase. Real live writes, Docker image/container/volume verification and actual installed mobile/Safari behavior belong to the subsequent deployment/final QA phase. AI fallback was disabled during this reliability phase; the subsequent [Gemini migration](GEMINI.md) adds the optional server-only fallback. Closed-app Web Push stays disabled; in-app reminders remain active.

The current production-only npm audit reports zero vulnerabilities. The full audit reports five high development-only dependent entries from braces <=3.0.3 through Next ESLint. Its proposed fix downgrades the lint configuration across Next majors, so it is not applied. The initial sandbox audit could not contact the registry; the successful read-only audit was run with permitted network access. No packages were added for this review.
